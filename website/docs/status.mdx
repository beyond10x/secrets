Secrets 0.5.0 ships the service, its workload client, and the named-storage library over the OS
keychain and this service. **Shipped** means in a release and held by `task check`; **planned**
means specified and on the plan only.

## Known limitations

These describe 0.5.0 as it is.

### Audit actors can be caller-chosen

- `POST /v1/workload/secrets:delete` records the body's `actor` when one is given.
- A prepared batch records the prepare request's `actor` on every event its commit writes.
- `PUT /v1/workload/secrets` records the `owner_subject` the workload sets.

Treat those actors as claims of an authorized workload, not verified identities. A fix is planned.

### Other gaps

- No user route returns a value, whatever the disclosure; workload reads ignore disclosure.
- Serving requires Kubernetes: there is no local or development authority.
- Delete is not cryptographic erasure; backups stay decryptable with the keyring.
- Grant and keyring changes need a restart, and a workload subject acts in one tenant.
- Audit events cannot be read through the API; `/metrics` exposes only `secrets_up`.

## Named secrets over several backends

An in-process Rust library for **named** secrets such as `openai` or `team/openai`, with several
backends behind one interface. It is the `secrets.storage` domain of the
[specification](./reference/ess/secrets-storage.md), and its conformance suite runs on every check.

- **Scope.** Each secret belongs to one tenant, namespace and user, and is unique by scope and
  name. Names are `/`-separated segments of `a-z0-9._-`, at most 128 bytes and 64 per segment.
  Values are at most 1 MiB, or what the backend accepts.
- **Backends.** Each namespace is mounted on exactly one backend, with no fallback between them.
  The OS keychain and this service read, write, delete and list. This service as a backend maps a
  name to `{tenant, namespace, key = "<user>/<name>"}` with the user as owner, and holds values up
  to about 768 KiB.
- **Operations.** Add, remove and re-mount a namespace; bind and unbind a name; write, read,
  delete, rename; list metadata, never a value. The local authorizer allows tenant and user
  `default` and denies every other before any backend call. Errors are closed codes: `not-found`,
  `denied`, `unsupported`, `unavailable`, `invalid-name`, `too-large`, `conflict`.
- **Local CLI.** `secretsctl` runs these operations on this machine and never prints a value; it
  hands one over only as a new mode-0600 file (`read --out`). See
  [Getting started](./getting-started.md#local-cli).

## Planned: named secrets over several backends

:::info[Planned]
Nothing in this section is built; names and limits may change before it ships.
:::

- **1Password.** A read-only backend; a name is bound to a locator such as
  `op://<vault>/<item>/<field>` before it is read.
- **Also planned.** The verified principal on every audit event.
- **Not planned.** HashiCorp Vault as a backend, namespace-wide secrets without an owner, and an
  external authorization service.

## Build from source

```bash
git clone https://github.com/beyond10x/secrets.git
cd secrets
task check
```
